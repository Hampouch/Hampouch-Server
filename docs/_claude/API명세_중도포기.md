## `POST /api/challenges/{id}/give-up` — 중도 포기 🔒

대응 화면: 진행 중 챌린지 "그만두기".

**서버**: 대상 챌린지(IN_PROGRESS)를 `status = FAIL`로 즉시 종료. `end_date` 경과 조건과 무관하게 확정 → 이후 `GET /{id}/result` 조회 가능(`API명세_본챌린지.md` §4 result의 status 규칙에 대한 예외 경로). `end_date`는 원래 목표 기간 그대로 보존(자체 결정 — 기록 유지, 필요 시 PM 확인). 요청 바디 없음.

**만료 후 포기 요청**: 기간(endDate)이 지났는데 아직 확정 전(결과·히스토리를 안 열어 IN_PROGRESS로 남음)인 챌린지에
포기가 오면, §4의 lazy 확정을 먼저 적용해 계산 판정(SUCCESS/FAIL)으로 확정한 뒤 409를 낸다(자체 결정 — §4의
"조회 경로가 확정을 선행" 불변식과 일관). 기간을 다 채워 SUCCESS여야 할 챌린지가 뒤늦은 "그만두기"로 복구 불가 FAIL이
되는 것 방지. endDate 당일까지는 아직 기간 중이라 포기 가능.

**응답 `200 OK`**

```json
{ "challengeId": 1, "status": "FAIL" }
```

**에러**

| 코드 | 상황 |
|---|---|
| 401 | 인증 실패 |
| 403 | 남의 챌린지 |
| 404 | 챌린지 id 없음 |
| 409 | 이미 종료됨(IN_PROGRESS 아님 — 기간 경과분은 위 규칙대로 확정 선행 후 409) — `CHALLENGE_NOT_IN_PROGRESS` |

> **재계산과의 상호작용(구현됨)**: 종료 후 기간 내 지출을 수정하면 결과를 기록 기준으로 재계산하는 규칙(0714 확정)이 있는데,
> 포기의 FAIL은 기록에서 계산된 결과가 아니라 유저 선언이다. 그래서 종료 사유 컬럼(`challenge.end_reason` — `GIVEN_UP` / null=계산 판정)을
> 두고 포기 챌린지를 재계산에서 제외했다 — "포기한 챌린지의 지출을 수정했더니 기록상 전부 성공이라 SUCCESS로 부활"하는 버그 방지.
> 기록 수정 자체는 기간 내면 포기 챌린지도 허용(0711 PM "종료 후 자유 수정") — 제외되는 건 status 재계산뿐.

> ⚠️ **잠정 — 포기 챌린지의 결과·기록 금액 집계 구간(명세 공백, 질문목록 13번)**: 결과 화면(§4)과 지난 챌린지 카드의 집계 규칙은
> "기간 전체 + 미입력일=0원=성공"(0630 확정) 하나뿐인데, 포기는 endDate 전에 끝나므로 포기 이후 잔여일까지 전부 성공·절약으로 잡힌다.
> 예: 30일(예산 300,000원 → 한도 10,000원) 챌린지를 기록 없이 2일차에 포기하면, 상태는 FAIL인데 집계는 성공 30일 ·
> 절약 300,000원(30일 × 한도 전액)으로 표시된다. 현행 구현은 규칙 그대로(기간 전체) — PM 답에 따라 집계 구간만 조정(additive).
> 같은 뿌리의 파생: 포기 시각을 따로 저장하지 않아(endDate 보존), 히스토리의 "최근 종료 순" 정렬에서 포기 챌린지가
> 실제 포기 시점이 아니라 원래 endDate 자리에 배치된다 — 긴 챌린지를 일찍 포기하면 그 뒤에 완주한 짧은 챌린지보다 위에 뜰 수 있음. 질문 13에 병합.
