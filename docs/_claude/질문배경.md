# PM 질문 배경 노트 (Claude 작업용 — 번호는 PM_질문목록.md와 동기)

> PM_질문목록에는 질문 문장만 둔다(0715 일혁 지시). 배경·현행 서버 동작·후보 답·영향도·출처는 여기에.
> 회의 전 브리핑 때 Claude가 두 파일을 합쳐 안건으로 만든다. 질문이 해소되면 여기 항목도 같이 지운다.

## 1. 월급날 주기 모드
- 확정 이력: 0714 PM 답변 = 주기가 월급날로 맞춰짐 · 기간형은 일회성이라 무관 · 첫 주기는 부분 기간 가능. 0714 전체회의(11:00) = 기간 선택↔날짜 고정 상호 배타 UI · 온보딩 UI는 하루당 목표 입력→기간 내 총 목표 자동 계산 표시(서버 계약은 총액 budgetTotal 유지 — 안드가 환산해 총액 송신, 안드 확인 필요). 상세는 `결정기록.md` 해당 섹션.
- 입력 단위 질문의 배경: 현행 온보딩2 시안은 "기간 내 식비 목표"(총액) 직접 입력 + 하루 한도 미리보기 — 전체회의 확정(하루당 입력)과 어긋남. 시안 미반영인지 번복인지가 쟁점. PM보단 디자이너 확인 건일 수 있음.
- 리필 공식 후보: ⓐ 하루 한도 × 그 주기 일수(하루 1만원이면 31일 주기=31만원, 28일 주기=28만원 — 하루 한도 일정, 하루당 입력 UI와 자연스러움) ⓑ 직전 총액 그대로 리필(총액 일정, 하루 한도가 주기 길이 따라 변동).
- 후속(질문 아님): 답 나오면 안드와 생성 계약 재정의 협의 — durationDays 없이 paydayDay만 보내는 형태? 현 서버는 durationDays 필수의 중첩 구조라 월급날 동작 확정 때 함께 변경.

## 2. finalize/lock
- 출처: 스크린디자인 '지출 수정하기 / 챌린지 종료' 화면 — 디자이너 주석 "피엠님과 추가 논의 필요"로 디자인 자체 미확정.
- 잠금 질문의 맥락: 종료 후 수정 시 재계산은 0714 확정 — 잠금이 생기면 그 경계가 질문.
- 서버 영향: 확정되면 종료 확정 write API + 상태 전이 추가. 확정 전 구현 보류(#3~11과 독립).

## 3. 경고 카드 노출 규칙
- 현행 서버: 카드별 자기 트리거로만 발동(0713 오늘 사용률 게이트 제거). GOAL_TOO_TIGHT는 오늘 사용률 무관, 판정 완료 구간 3일 연속 초과.

## 4. 예산·하루 한도의 하한
- 현행 서버: budgetTotal ≥ 1만 검증. 저예산+장기간(50원·100일)이면 버림 나눗셈으로 하루 한도 0원 챌린지 성립(지출 0원인 날만 성공).
- 무지출 챌린지: 예산 0원 = 지출 0원만 성공 — 실존하는 절약 방식이라 지원 의도 확인. 지원하면 UI 문구·절약액 표시(항상 0원) 기획 필요. 확정 전까지 서버는 0원 금지(@Min(1)) 유지 — 미입력 사고와 구분 안 되는 값. 블로커 아님(계산은 0 방어로 동작).

## 5. 경계값 소속
- 30/70 숫자는 0714 확정, 경계값 소속은 명시된 적 없음. 현행 서버: 경계값 = 윗구간 시작(정확히 30% = 주의 시작, 70% = 위험 시작, 29.9% = 안심) — 캐릭터·경고 등급 동일. 반대로 확정되면 부등호 한 곳 수정, 블로커 아님.

## 6. 연속 달성 표시
- 현행 서버: 최장 연속(maxStreak)을 내려줌. 예: 9일 연속 성공 후 5일 연속 초과 실패 → 최장 기준 "9일", 마지막 기준 "0일". 성공 화면 시안은 두 값이 같은 사례(14일 전부 성공)라 판별 불가. 반대로 확정되면 계산 한 곳 수정, 블로커 아님.

## 7. 성공/실패 판정 기준 ★ 영향 최대
- 현행 서버: 초과일이 하루라도 있으면 실패. 예: 한도 2만·14일(예산 28만)에서 9일 성공+5일 초과, 총지출 259,100원(예산 미만) → 실패 판정.
- 실패 화면 시안(9/14 성공 사례)은 현행 전제와 부합하나 명시 확정 기록 없음. 총액 기준으로 확정되면 판정·집계 근간 수정 — 7/20에 최우선 확인 권고.

## 8. 도장 달력 달 넘김
- 서버 영향 없음(calendar가 year/month 파라미터라 어느 쪽이든 대응). 안드 구현 참고용.

## 9. 추천 미니 카탈로그 (#10)
- 0630 "기획 리스트업 확정"이라는데 실물 리스트가 서버에 전달된 적 없음 → 임시 시드 12건(기간 1·3·7·14·31 커버)으로 구현. 교체 시 서버 작업: 시더가 빈 테이블에만 심는 구조라 `recommended_mini_challenge` 비우고 재기동.
- 현행 서버: 전체 셔플 반환. 블로커 아님.

## 10. 미니 챌린지 (#9)
- 중복 409: 추천/커스텀 통일(origin 없음, 0707)이라 같은 추천인지 식별 자체가 불가 — 확정하려면 ERD 변경(origin 재도입 등) 수반. 현재 미구현(중복 추가 허용).
- 제목 길이: 명세·ERD에 없어 잠정 255자(DB 컬럼 한계), 초과 400.
- 미래 날짜: ~~허용(잠정)~~ → **0716 400 차단(`MINI_FUTURE_DATE`)으로 전환 — 일혁 제안, 자체 확정.**
  근거는 확정 둘의 준용: ① 홈 날짜 스트립 미래 이동 불가(0711 PM 확정 — 미니 홈도 같은 스트립 컴포넌트),
  ② 미니 미래 체크 400(0707 일혁 확정, "선체크 상황 없음")과 동일 논리 — 미래 '조회'도 일어날 상황이 없고,
  열어 두면 클라 날짜 버그가 그럴싸한 빈 응답으로 조용히 넘어간다. 확정 준용이라 PM 질문에서 내림(질문목록
  10번에서 삭제). 코드명 MINI_FUTURE_DATE는 자체 결정(안드 확인 시 맞춤).
- 스트릭: 현 서버는 조회일 미완료 시 전날까지 연속(§1 예시 checkedCount 3/4 + streakDays 3). 전부 블로커 아님.
- 스트릭(과거 조회일): 서버는 조회일이 과거여도 오늘과 똑같이 건너뜀 — 명세 예시가 오늘 케이스만 시연해서
  가장 단순한 일관 규칙로 잠정 구현(0716). 쟁점 = 스트릭이 "그 날짜 화면의 값"(현행)이냐 "유저의 단일 사실"(과거는 판정→0,
  통상 스트릭 제품 문법)이냐. 과거 화면이 streakDays를 안 쓰면 논쟁 자체가 무의미라 [안드 확인]이 선행.
  판정으로 확정 시 서비스가 실제 오늘 여부를 계산기에 넘기는 소규모 수정(계산기 순수성은 파라미터로 유지).
- 피그마 실측(0716, REST 스냅샷 + 렌더 판독):
  - **과거 날짜가 선택된 미니 홈 시안 = 0장** — 최종 4장·초안 10장 전부 가운데 날짜(=오늘) 선택 상태만 존재.
    즉 과거 화면의 streakDays 표시값은 시안이 정의하지 않음. 단 "연속 달성 N일째" 배지가 날짜바와 **같은 고정
    히어로 카드 안**에 있어(숨김 변형 없음), 안드가 따로 숨기지 않는 한 과거 날짜에서도 배지 자체는 표시됨.
  - 빈 상태 시안(활성 미니 0개, "진행중인 챌린지가 없어요")에 **"연속 달성 3일째"가 그대로 표시** — 조회일이
    미충족(활성 0)이어도 스트릭이 유지·표시됨을 시안이 직접 시연 = 현행 조회일 스킵 규칙과 일치(당일 케이스 한정).
    "연속 달성 0일째" 변형도 별도로 존재(신규 유저).
  - 파일 전체에서 유일하게 그려졌던 과거 날짜 화면(메인 홈 04.11~13, 스크린디자인 페이지)은 X 라인 2개로
    지워지고 "챌린지 기간 외 이전 날짜에는 접근 불가, 불필요해진 화면으로 X처리" 주석(1759:13011)이 붙음 —
    과거 접근을 좁히는 방향의 결정 흔적(본챌 맥락이지만 파일 내 유일한 과거 날짜 명시 규칙).
- 본챌 교차 확인(0716, 같은 날 일혁 재지적으로 ① 보정): "본챌처럼 하면 되지 않나"의 답 = **이동은 확정,
  스트릭 값 규칙은 본챌도 미정.**
  ① 서버 — **과거 이동 자체는 확정이 맞음**(0711 PM: 홈 날짜 스트립 미래 이동 불가·전날 이동 시 "전날 시점의
  정보" 표시·본챌 카드도 as-of 조회 필요 / 0707: 이동은 챌린지 기간 내만 — 결정기록.md). 단 서버 구현이 아직
  없음 — `GET /current`엔 `date` 파라미터가 없고 "확장 예정(설계 초안, 구현 이슈로)" 상태. 그래서 과거 조회일의
  스트릭 '값 산정 규칙'((a)/(b))은 본챌에도 아직 없어 따라 할 대상이 없다. 참고: 확정 문구 "전날 시점의 정보를
  표시"는 그날 봤던 화면을 재구성하는 스냅샷 철학이라 (a)와 결이 같음 — 결정적 근거는 아니나 팀 결정 중 가장
  (a) 쪽 신호. ② 시안 — 메인 화면 7장도 전부 가운데(오늘)만 선택(ON), 과거 선택 상태 0장.
  ③ 당일 처리는 이미 본챌을 따름 — 미니의 조회일 스킵 규칙 자체가 본챌 홈 "오늘은 기록 있을 때만 포함"(0714 확정)과
  같은 사상. ④ 단 과거 미기록일 기본값은 정반대(본챌: 미기록=0원=성공 / 미니: 미체크=끊김)라 본챌 규칙을 문자
  그대로 이식하는 건 불가능하고, (a)/(b) 차이의 실익도 미니 쪽이 훨씬 큼. → 7/20에 물을 때 **본챌 date 확장의
  과거 조회일 처리와 묶어서 한 번에** 정하면 두 도메인이 안 갈라짐.
- 카드 "N/7일"의 의미(0716 피그마 실측 — 처음 "itemStreak 미사용 의심"이라 적었다가 재검증 후 정정):
  카드 우측 슬롯(레이어명 '기간', 1일짜리는 "오늘만")의 값이 무엇의 카운트인지 시안만으론 미확정. 후보 3개와 증거:
  - (가) **경과일**(progressDays/durationDays — 현행 명세 §1의 해석): 레이어명이 '기간'인 점은 부합하나,
    아래 두 증거와 상충 — 경과일은 체크한다고 변하지 않는데 시안 쌍은 변한다.
  - (나) **누적 체크 일수**: ①미체크 카드 = 항상 "2/7일", 체크된 카드 = 항상 "3/7일" — 와이어프레임 이후
    3세대 12곳 전수에서 예외 없음(체크 → +1 쌍). ②파일 전체의 N/M 관용이 달성/기간 — 성공 화면 "14/14"에
    **"성공한 날"** 라벨 명시, 지난 챌린지 목록 "3/14"(실패)도 누적 성공일. → 현재 가장 유력.
    **확정되면 §1 items에 누적 체크일수 필드 추가 필요**(mini_challenge_day count ≤ date, 소규모).
  - (다) **현재 연속**(itemStreak): 체크 +1 쌍과는 일치(와이어프레임 카드가 "🔥 N일 연속"이었던 계보).
    단 (나)의 관용 증거와 겹치는 예시값(연속 2 = 누적 2)이라 구분 불가 — 시안 예시로는 차순위.
  - 서버 영향: (나)면 필드 추가, (다)면 itemStreak 그대로 사용, (가)면 itemStreak가 표시처 없는
    미사용 필드가 됨(제거 후보). 어느 쪽이든 블로커 아님 — 안드 렌더링 확인이 선행.
- 삭제 진입점(0716 피그마 실측): 미니 관련 최종 시안 전체에서 '삭제' 텍스트/버튼 0건 — §4 DELETE는 0630 회의
  확정이라 서버는 그대로 제공하면 되고, 진입점은 디자인/안드 몫의 홀. 블로커 아님.
