## 1. 월급날 주기 모드
- 확정 이력: 0714 PM 답변 = 주기가 월급날로 맞춰짐 · 기간형은 일회성이라 무관 · 첫 주기는 부분 기간 가능. 0714 전체회의(11:00) = 기간 선택↔날짜 고정 상호 배타 UI · 온보딩 UI는 하루당 목표 입력→기간 내 총 목표 자동 계산 표시(서버 계약은 총액 budgetTotal 유지 — 안드가 환산해 총액 송신, 안드 확인 필요). 상세는 `결정기록.md` 해당 섹션.
- 입력 단위 질문의 배경: 현행 온보딩2 시안은 "기간 내 식비 목표"(총액) 직접 입력 + 하루 한도 미리보기 — 전체회의 확정(하루당 입력)과 어긋남. 시안 미반영인지 번복인지가 쟁점. PM보단 디자이너 확인 건일 수 있음.
- 리필 공식 후보: ⓐ 하루 한도 × 그 주기 일수(하루 1만원이면 31일 주기=31만원, 28일 주기=28만원 — 하루 한도 일정, 하루당 입력 UI와 자연스러움) ⓑ 직전 총액 그대로 리필(총액 일정, 하루 한도가 주기 길이 따라 변동).
- 후속(질문 아님): 답 나오면 안드와 생성 계약 재정의 협의 — durationDays 없이 paydayDay만 보내는 형태? 현 서버는 durationDays 필수의 중첩 구조라 월급날 동작 확정 때 함께 변경.

## 4. 예산·하루 한도의 하한 + 금액 상한
- 현행 서버: budgetTotal ≥ 1만 검증. 저예산+장기간(50원·100일)이면 버림 나눗셈으로 하루 한도 0원 챌린지 성립(지출 0원인 날만 성공).
- 무지출 챌린지: 예산 0원 = 지출 0원만 성공 — 실존하는 절약 방식이라 지원 의도 확인. 지원하면 UI 문구·절약액 표시(항상 0원) 기획 필요. 확정 전까지 서버는 0원 금지(@Min(1)) 유지 — 미입력 사고와 구분 안 되는 값. 블로커 아님(계산은 0 방어로 동작).
- **상한 질문의 배경(0715 나연 PR #17 리뷰에서 유입)**: `budgetTotal`은 `@Min(1)`만, `spentAmount`는 `@Min(0)`만 걸려 있어 **둘 다 상한이 int 최대(21.4억)**. `ChallengeCalculator.summarizeForResult`의 `actualSpent`·`overAmount`가 **int 누산기로 최대 100일치를 더하므로** 11억짜리 2일이면 음수로 뒤집힘(검증 완료 — 실재하는 오버플로우). `savedAmount`는 `dailyLimit × 일수 ≈ budgetTotal`로 묶여 경계상 안전.
- 나연 제안 = **@Max 추가 또는 금액 타입 long 통일** 택1. 비교: **@Max**는 국소 수정이고 `durationDays @Max(100)`(0714 전체회의) 선례와 같은 결이지만 **상한값이 기획 값**이라 답이 필요. **long 통일**은 엔티티 컬럼(BIGINT)·ERD(진실=ERDCloud)·령준 EXPENSE 금액 타입 계약까지 번져 **팀 결정** — 명세 §0도 "금액: 정수(원)". → 답 오면 @Max가 유력, 값만 받으면 즉시 반영 가능. 블로커 아님(실사용 금액대에선 발생 불가).

## 5. 경계값 소속
- 30/70 숫자는 0714 확정, 경계값 소속은 명시된 적 없음. 현행 서버: 경계값 = 윗구간 시작(정확히 30% = 주의 시작, 70% = 위험 시작, 29.9% = 안심) — 캐릭터·경고 등급 동일. 반대로 확정되면 부등호 한 곳 수정, 블로커 아님.

## 6. 연속 달성 표시
- 현행 서버: 최장 연속(maxStreak)을 내려줌. 예: 9일 연속 성공 후 5일 연속 초과 실패 → 최장 기준 "9일", 마지막 기준 "0일". 성공 화면 시안은 두 값이 같은 사례(14일 전부 성공)라 판별 불가. 반대로 확정되면 계산 한 곳 수정, 블로커 아님.

## 7. 성공/실패 판정 기준 ★ 영향 최대
- 현행 서버: 초과일이 하루라도 있으면 실패. 예: 한도 2만·14일(예산 28만)에서 9일 성공+5일 초과, 총지출 259,100원(예산 미만) → 실패 판정.
- 실패 화면 시안(9/14 성공 사례)은 현행 전제와 부합하나 명시 확정 기록 없음. 총액 기준으로 확정되면 판정·집계 근간 수정 — 7/20에 최우선 확인 권고.
- 11번(무효 규칙)과 이웃 — 둘 다 "그날을 어떻게 세나"를 건드리지만 층이 다르다(7번=초과일 판정, 11번=미기록 시 챌린지 무효화). 독립적으로 답해도 모순은 안 생김. 같은 자리에서 물으면 효율적인 정도.

## 11. 배틀 무효 규칙의 본챌린지 이식 (0715 PM 확정 — 잔여 정의만 질문)
> 배틀 2안 원문: 1일→알림 / 2일→경고 / **연속** 3일→무효(누적X) · 무효자 순위·벌칙 제외·복귀 불가 · **7일 이상 배틀만** · 남은 인원 1명이면 배틀 무효 · "오늘은 안 썼어요"=기록 인정.
> **0715 확정 경위**: 일혁이 PM에 "본챌린지는 미입력을 무조건 0원 입력으로 당일 성공 처리 중"이라고 충돌을 먼저 알림 → PM 답 "**본 챌린지도 같은 알림 로직에 멘트만 바꾸는 걸로 가능할까요? 이렇게 가면 챌린지 무효 화면도 하나 필요합니다.**" → 이식·화면 신설 확정, 0714 "기록 0건 챌린지=성공"은 **PM이 알고 개정하는 것**(충돌 자체는 쟁점 아님).

### 이식 대상에서 자연 탈락 (질문 아님 — 배틀 전용 조항)
"순위·벌칙 제외" · "남은 인원 1명이면 배틀 무효" · "타 참가자용 '00님 무효' 알림" · "무효자 회색+순위 밖 영역"은 전부 **다인·순위·벌칙 전제**. 본챌린지는 솔로라 대응물이 없어 그대로 빠짐(PM "멘트만 변경" = 배틀 전용 조항 비이식). 알림 4종 → 본챌은 **3종**(1일차/2일차/3일차), 예외 로직 2건 → **1건**(짧은 챌린지 제외).

### 서버 작업 규모 = 작음 (additive — 0715 재계산, 첫 평가의 "판정 근간 전복"은 과장이었음)
- 1~2일 미기록이 계속 성공이라면 `ChallengeCalculator`의 `d == null ? SUCCESS` **3곳은 그대로 유지**된다. 무효는 3일 연속에서 챌린지 자체를 끝내는 것이라 성공/실패 판정과 **층이 다름** → 공존 가능.
- 필요한 것: `ChallengeStatus`에 **VOID 추가**(현 IN_PROGRESS/SUCCESS/FAIL의 4번째) · 연속 미기록 카운트(기존 `trailingStreakAsOf`와 같은 패턴, 행 유무로) · 무효 판정 시점(스케줄러 or 조회 시 lazy — 현행 result가 lazy 확정 방식이라 선례 있음).
- 데이터 모델은 이미 구분 가능: `ChallengeService.getCurrent`가 `Optional<ChallengeDay> todayRow`로 **행 유무**를 들고 있음(미기록 = 빈 상자, 0원 입력 = 행 있고 spent=0).
- 단, `give-up`(#3)의 "포기 FAIL은 재계산에서 제외" 주의사항과 같은 층 — VOID도 재계산으로 부활하면 안 됨(종료 사유 표식 필요). 두 이슈를 같이 설계할 것.

### ⛔ 진짜 선결 조건 2개 (PM 질문 아님 — 팀·서버팀 건)
1. **"미기록" 감지 수단이 운영에 없음 (령준 계약)** — 이게 이식의 유일한 실질 블로커.
   - 운영 지출 출처 = **령준 EXPENSE 조회 메서드**(0707 서버팀 확정), `POST /days`는 시드 전용 강등. 현 계약은 **'합계'만** 넘김 → **합계 0원이 "안 썼다"인지 "입력 안 했다"인지 구분 불가**. 무효 판정의 입력 자체가 없는 셈.
   - "오늘은 안 썼어요" = **지출 입력 화면(령준 파트)** 기능이고, 령준 메서드가 그 구분(기록 건수 또는 무지출 선언 플래그)을 넘겨줘야 함 → **서버팀 계약 신규**. 7/20 BE 회의 안건.
2. **알림 도메인 부재** — PM이 재사용을 전제한 "같은 알림 로직"이 **아직 아무 데도 없음**(배틀도 미구현). 분담표상 '보류·담당 미정'·ERD 제외, 0714 BE "차후 추가". 0715 코드 실측: `@Scheduled` 0건(develop·feat/1) · 알림/FCM 코드 0건 · build.gradle firebase/quartz 없음. 인프라는 **나연 담당**(일혁 브랜치 수정 금지).
   - → PM 답변안: 무효 **판정·상태·화면 데이터**는 알림과 무관하게 먼저 넣을 수 있음. 알림 3종·팝업 2종만 알림 도메인 뒤로.

## 12. 지난 챌린지 기록 카드 (#4)

- **수정 규모**: 전부 additive(필드 추가·필터 완화)라 작음. 블로커 아님 — 안드 확인 전까지 현행 유지.

## 13. 포기 챌린지의 결과 집계 구간 (#3)
- **출처**: 0717 중도 포기(#3) 구현 중 발견 — 명세 공백. 포기의 status 규칙(즉시 FAIL·재계산 제외)은 0707 확정대로 구현했으나, 결과·기록 화면의 **금액 집계를 어디까지 셀지**는 어느 회의에서도 안 다뤄짐.
- **현행 동작**: 결과 화면(§4)·히스토리 카드의 집계 규칙은 "기간 전체 + 미입력일=0원=성공"(0630 확정) 하나뿐이라 포기 챌린지도 원래 endDate까지 집계한다. 포기는 endDate 전에 끝나므로 포기 이후 잔여일이 전부 '성공한 날'·절약액으로 잡힘 — 예: 30일(한도 10,000원) 챌린지를 기록 없이 2일차에 포기하면 상태는 FAIL인데 성공 30일·절약 300,000원(전액)으로 표시.
- **후보**: (a) 기간 전체 유지(현행 — 수정 0) (b) 시작~포기일까지만 집계(포기 시점 저장 컬럼 필요 — end_reason처럼 additive) (c) 포기 챌린지는 금액 집계 숨김(화면 결정 필요 — 시안에 포기 카드 없음).
- **같은 뿌리의 정렬 파생(0717 검증에서 발견)**: 포기 시각을 저장하지 않고 endDate를 보존하므로, 히스토리 "최근 종료 순"(endDate 내림차순) 정렬에서 포기 챌린지가 실제 포기 시점이 아니라 원래 endDate 자리에 배치된다 — 예: 07-17에 30일 챌린지(endDate 08-15)를 포기 → 07-24에 7일 챌린지 완주 → 리스트에서 포기한 쪽이 위. 집계 구간 답에 (b)를 고르면 같은 컬럼으로 정렬도 해결 가능 — 함께 물을 것.
- **블로커 아님**: 어느 답이든 additive 수정. 답 전까지 (a)로 동작하고, 테스트는 집계 필드를 단정하지 않게 작성해 둠(통합 giveUpFlow 주석 참조).

## 14. 중도 포기 진입점·경계 (#3)
- **출처**: 0717 피그마 전수 실측(스크린디자인 72:5 + 와이어프레임 0:1 — 콘텐츠 타일 40장 전수 판독, 빈 타일은 비율 로그로 스킵 증명) — **"그만두기/포기" UI가 두 페이지 모두에 없음.** 가장 근접한 것은 휴식 모달("잠깐 쉬어갈까요?" — 챌린지 '사이' 휴식)과 배틀 무효·미입력 자동취소 모달뿐. 0707 전체회의 결정("도중 중단 없음, 그만두면 실패")은 있는데 그 버튼이 붙을 화면 시안이 없다. 서버 API(POST /give-up)는 결정 기반으로 구현 완료 — 진입점이 어디로 정해져도 서버 수정 0.
- **만료 후 포기(잠정 — 자체 결정)**: 기간이 끝났지만 lazy 확정 전(IN_PROGRESS로 남음)인 챌린지에 포기가 오면 계산 판정으로 먼저 확정한 뒤 409. 근거: 기간을 다 채워 성공인 결과가 뒤늦은 그만두기로 복구 불가 FAIL이 되는 것 방지 + "조회 경로가 확정을 선행"하는 기존 불변식과 일관. 이 경계는 어느 회의에서도 안 다뤄짐 — 안드가 만료 후 그만두기 버튼을 숨기면 실질 도달 불가 경로라 우선순위 낮음.
- **포기 챌린지 지출 수정(해석 적용)**: 0711 PM "종료 후 자유 수정"은 종료 일반에 대한 답 — 포기도 종료의 하나로 해석해 수정 허용. 재계산 제외(end_reason 가드)는 부활 버그 방지의 자체 설계. 포기 챌린지만 수정 금지로 답이 나오면 서버 한 줄 추가로 대응.
- **블로커 아님**: 서버는 어느 답에도 additive 대응.
