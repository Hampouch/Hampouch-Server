## 1. `POST /api/rests` — 휴식 시작 🔒

대응 화면: 휴식 시작("잠깐 쉬어갈까요?"). **유저 단위** — 챌린지 리소스 하위가 아님.

**요청 바디**

| 필드 | 타입 | 필수 | 제약 / 설명 |
|---|---|---|---|
| restDays | int | ✅ | 1 ~ 3650 · 화면의 3일/1주/2주/직접선택을 **일수로 통일** · ⚠️상한 3650(10년)은 기획값이 아니라 서버 방어값(잠정) — 복귀 예정일이 MySQL DATE 상한(9999-12-31)을 넘는 500 방지, 기획 상한이 정해지면 값 교체(PM_질문목록 15번) |

**서버**: `user_rest` 행 생성 — `rest_start_date = 오늘`, `planned_resume_date = 오늘 + restDays` (챌린지 endDate의 −1과 달리 −1 없음 — 예시 그대로 07-06 + 7 = 07-13)
휴식 중엔 챌린지가 없으므로 한도 체크·미입력 알림·미니 챌린지는 자연히 없음(별도 상태 전이 불필요).

**응답 `201 Created`** (헤더 `Location: /api/rests/{id}` — ✅자체 결정: 생성 API 관례(본챌 §1)와 통일. 단 `GET /api/rests/{id}`는 미구현이라 역참조 불가)

```json
{ "restId": 3, "restStartDate": "2026-07-06", "plannedResumeDate": "2026-07-13" }
```

**에러**

| 코드 | 상황 |
|---|---|
| 400 | restDays < 1 또는 > 3650(서버 방어값·잠정) |
| 401 | 인증 실패 |
| 409 | 이미 휴식 중(종료 안 된 `user_rest` 존재, `REST_ALREADY_ACTIVE`) · **진행 중(IN_PROGRESS) 챌린지가 있으면 409**(`CHALLENGE_ALREADY_IN_PROGRESS`) — ✅화면 확정(휴식 진입점 = 결과 화면뿐, 2026-07-07). 진행 중 판단은 만료 미확정 챌린지를 §4 규칙으로 먼저 확정한 뒤(lazy 확정 — 포기·히스토리와 동일 원리) 내린다. ⚠️0718 시안 긴장 발견(질문 15 여섯째): 휴식 시작 화면 문구("챌린지만 멈출 뿐"·"취소하고 챌린지 계속할래요")가 진행 중 진입을 시사 — 확정 번복인지 구 카피 잔재인지 확인 전까지 409 유지 |

> **"열린(종료 안 된) 휴식"의 판정(✅자체 결정)**: `actual_resume_date`가 없거나 **기준일보다 뒤**면 열림.
> "내일부터(TOMORROW)"를 고른 당일은 actual이 내일이라 여전히 휴식 중 — §2·§3·자동 종료가 전부 이 술어 하나를 공유한다.

> **배타 규칙(반대 방향, ✅자체 결정)**: 휴식 중에 `POST /challenges`(새 챌린지 생성)가 오면 **휴식을 자동 종료**(`actual_resume_date = 오늘`)하고 생성 진행 — "다시 챌린지 시작하기" 흐름. "진행 중 챌린지 + 열린 휴식" 동시 상태는 존재하지 않게 유지(만약 데이터가 꼬이면 `GET /current`는 **진행 중 챌린지 우선**).

## 2. `POST /api/rests/resume` — 복귀 / 더 쉬기 🔒

대응 화면: 복귀 팝업("다시 돌아오신 걸 환영해요!") — 세 선택지를 이 API 하나로 처리. 복귀는 "재개"가 아니라 **휴식 종료 기록**이며, 새 챌린지 생성은 별도로 `POST /challenges`.

**요청 바디**

| 필드 | 타입 | 필수 | 제약 / 설명 |
|---|---|---|---|
| when | string | ✅ | `NOW`(지금 바로) / `TOMORROW`(내일부터) / `EXTEND`(조금 더 쉴게요) |
| extendDays | int | 조건부 | 1 ~ 3650, `when=EXTEND`면 필수 · ✅자체 결정: 기간 재선택 → 예정일 연장 · ⚠️상한은 §1 restDays와 같은 서버 방어값(잠정) |

**서버 동작 (when별)**

| when | 동작 |
|---|---|
| `NOW` | `actual_resume_date = 오늘` — 휴식 종료. 클라는 챌린지 생성 화면으로 이동 |
| `TOMORROW` | `actual_resume_date = 내일` — 내일부터 휴식 종료로 취급(오늘은 휴식기 홈 유지). ⚠️잠정(질문 15): "내일 종료 확정"(다음날 팝업 재노출 없음) 해석 — 근거: 미루기 해석이면 EXTEND 1일과 동일해져 버튼이 잉여. 미루기(다음날 재노출)로 확정되면 planned=내일·actual 없음으로 전환(서버 몇 줄) |
| `EXTEND` | `planned_resume_date += extendDays` — 휴식 계속. ⚠️자체 결정(잠정, PM_질문목록 15번): 잡혀 있던 복귀 예약(`actual_resume_date`)도 **취소(null로 되돌림)** — TOMORROW 상태에서 연장했는데 내일 휴식이 끝나 버리는 모순 방지. ⚠️0718 실측: "조금 더 쉴게요" 후속 **일수 선택 화면이 스크린디자인에 없음** — extendDays(기간 재선택) 계약 자체가 자체 결정. 시안대로 선택이 없다면 클라는 EXTEND 호출 없이 팝업만 닫는 구조(다음 실행 때 재노출)일 수 있음 — 확정 시 이 행 재검토 |

> TOMORROW를 고른 **당일은 아직 휴식 중**(§1 열림 판정)이라 다시 골라 바꿀 수 있다(✅자체 결정) —
> NOW로 당기면 `actual = 오늘`, EXTEND면 예약 취소 + 예정일 연장. NOW로 끝낸 뒤에는 열린 휴식이 없어 404.

**응답 `200 OK`**: `{ "restId": 3, "resumeDate": "2026-07-07" }` (`EXTEND`면 `{ "restId": 3, "plannedResumeDate": "..." }`)

**에러**: 400(when 오류 · EXTEND인데 extendDays 없음/상한 초과 = `VALIDATION_ERROR` · 반복 연장으로 예정일이 날짜 상한 9999년을 넘게 되는 요청 = `BAD_REQUEST` — 누적 가산이라 요청당 상한만으로는 못 막는 500 경로 컷) / 401 / 404(휴식 중 아님, `REST_NOT_ACTIVE`).

## 3. 휴식 중의 `GET /challenges/current` 응답

휴식 중이면 current가 404가 아니라 `200 OK`로 휴식기 홈 데이터를 준다(진행 중 챌린지가 있으면 그쪽 우선). **위젯도 current 재사용 예정**(팀 협의).

| 유저 상태 | 응답 |
|---|---|
| 진행 중 챌린지 있음 | 기존 응답 그대로(`API명세_본챌린지.md` §2) |
| **휴식 중** | `200 OK` — `challenge: null` + `rest` + `keptRecords` |
| 챌린지도 휴식도 없음 | 404 (기존 정책 유지) |

```json
{
  "challenge": null,
  "rest": { "restStartDate": "2026-07-06", "plannedResumeDate": "2026-07-13" },
  "keptRecords": { "savedAmount": 68200, "maxStreak": 14 }
}
```

- `keptRecords` = **직전 종료 챌린지의 결과**(총 절약·최고 연속 — 휴식기 홈 "보관 중인 내 기록" 표시값, 저장 없이 계산).
  - 집계 규칙은 결과 화면(§4)·히스토리와 **동일한 단일 출처**(전 기간 · 미입력일=0원=성공) — 직전 결과 화면에서 본 숫자와 항상 일치.
  - ⚠️ **집계 대상은 잠정**(PM_질문목록 15번, 0719 등재) — 시안 행 라벨("누적 절약 금액"·"최고 연속 달성")은 **역대 챌린지 전체 누계**로도 읽힌다. "직전 하나" 해석의 근거(와이어프레임 숫자 = 직전 성공 결과 화면 숫자)는 목업의 종료 챌린지가 1개면 두 해석을 구분 못 함. 역대 누계로 확정돼도 응답 모양은 동일 — 계산만 교체.
  - "직전"의 선정은 종료일이 아니라 **생성 순서(createdAt)** 기준(✅자체 결정) — 중도 포기 챌린지는 `end_date`가 원래 목표 기간 그대로 미래로 남아, 종료일 정렬은 "예전에 포기한 긴 챌린지"를 직전으로 오판한다(동시 진행 1개 규칙이라 생성순 = 종료순). 같은 뿌리의 정렬 문제는 PM_질문목록 13번.
  - 종료 챌린지가 하나도 없으면(정상 흐름에선 불가능 — 시드·데이터 꼬임 대비) `{ "savedAmount": 0, "maxStreak": 0 }` ⚠️자체 결정(잠정, PM_질문목록 15번).

## 잠정 / 확정 요약

| 항목 | 현재 상태 |
|---|---|
| 휴식의 의미 | ✅ 챌린지 사이 공백(유저 단위) — 진입점 = 결과 화면(화면 확정) · 보관 기록 산정은 아래 keptRecords 행(⚠️잠정) |
| 진행 중 휴식 진입 | ✅ 불가(409) — 진입점이 결과 화면뿐(2026-07-07 화면) · 만료 미확정 챌린지는 확정 후 판단(lazy 확정) |
| 휴식 중 새 챌린지 생성 | ✅ 휴식 자동 종료(`actual = 오늘` — 챌린지 시작일이 미래여도 오늘) 후 생성 진행 · current는 진행 중 우선 (자체 결정) |
| 열린 휴식 판정 | ✅ `actual_resume_date`가 없거나 기준일보다 뒤 — TOMORROW 당일은 여전히 휴식 중·재선택 가능 (자체 결정) |
| 휴식 상한·횟수 | ✅ 횟수 무제한 · ⚠️ 일수는 서버 방어값 3650 상한(잠정 — 기획 상한 나오면 교체, PM_질문목록 15번) |
| "조금 더 쉴게요" | ✅ 기간 재선택 → `planned_resume_date += extendDays` (자체 결정) · ⚠️ 복귀 예약 취소 포함(잠정, PM_질문목록 15번) |
| keptRecords | ⚠️ 직전(생성순) 종료 챌린지의 결과로 계산, 결과 화면과 동일 규칙 — 집계 대상(직전 하나 vs 역대 누계)은 잠정(PM_질문목록 15번) · ⚠️ 직전 없으면 0·0(잠정, 15번) |
