# 본 챌린지 — 테스트 시나리오 / 수용 기준

> 목적: 스텁+시드 단계에서 **판정·결과 로직을 검증**할 구체 예시(입력 → 기대 출력). Claude Code 단위 테스트 작성용.
> Figma 성공/실패 화면 숫자와 일치하도록 구성(작성 당시 시안 기준 — 시안의 예시 숫자는 이후 바뀔 수 있고, 검증 대상은 공식).
> 유지 규칙: 수용 기준이 바뀌는 확정이 나오면 이 문서도 같이 갱신한다 — 테스트 코드와 이중 장부가 되면 안 됨(예: 0714 기간 100일 상한).
> (2026-07-06: 휴식 재해석 — 휴식은 챌린지 사이 공백이라 이 문서의 409 조건은 원래대로 유효. PAUSED 관련 주의는 철회됨)

## 공통 규칙
- 일별 판정: `spent ≤ dailyLimit` → `SUCCESS`, 아니면 `OVER`
- `dailyLimit = floor(budgetTotal / durationDays)`
- `savedAmount = Σ max(0, dailyLimit − spent)` · `overAmount = Σ max(0, spent − dailyLimit)`
- 챌린지 status: 종료(end_date 경과) 후 전부 SUCCESS면 `SUCCESS`, OVER 1일+이면 `FAIL`

---

## S1. 성공 (성공 화면과 일치)
- **입력**: `durationDays=14`, `budgetTotal=280000` → `dailyLimit=20000`
- **일별 지출(14일)**: `15000` ×13일 + `16800` ×1일 (합 211,800, 모두 ≤ 20,000)
- **기대**: `status=SUCCESS`, `successDays=14`, `overDays=0`, `savedAmount=68200`, `overAmount=0`, `maxStreak=14`
- 대조: 화면 "+68,200원 총 절약 / 14·14 / 목표 280,000 → 실제 211,800"

## S2. 실패 (실패 화면과 일치)
- **입력**: `durationDays=14`, `budgetTotal=280000` → `dailyLimit=20000`
- **일별 지출**: 성공 9일(각 ≤ 20,000) + 초과 5일 `25000·25000·25000·25000·24100` (초과분 합 = 24,100)
- **순서(고정)**: 성공 9일 연속 → 초과 5일 → `maxStreak=9`
- **기대**: `status=FAIL`, `successDays=9`, `overDays=5`, `overAmount=24100`, `maxStreak=9`
- 대조: 화면 "9 성공 / 5 초과 / +24,100 초과"

## S3. 판정 경계값
- `spent == dailyLimit` → `SUCCESS` (≤ 이므로)
- `spent == dailyLimit + 1` → `OVER`

## S4. 한도 나눗셈 버림
- `budgetTotal=100000`, `durationDays=30` → `dailyLimit=3333` (floor)
- Σ한도 = 99,990 < 100,000 은 **의도된 동작**(버림). 화면의 "하루 3,333원"과 일치.

## S5. 진행 중 결과 요청
- `end_date` 이전에 `GET /challenges/{id}/result` → **409** (결과 미확정)

## S6. 생성 검증 (`POST /challenges`)
- `durationDays < 1` 또는 `budgetTotal < 1` → **400**
- `durationDays > 100` → **400** (0714 전체회의 확정: 기간 입력 한도 100일)
- `resetByPayday=true` 인데 `paydayDay` 없음 → **400**
- 이미 `IN_PROGRESS` 챌린지 존재 → **409**

## S7. 일별 입력 검증 (`POST /challenges/{id}/days`)
- `date`가 챌린지 기간 밖 → **400**
- `spentAmount < 0` → **400**
- 같은 `date` 재호출 → upsert(덮어쓰기), 200
