# 본 챌린지 — 백엔드 설계 초안 (정일혁 파트)

> 범위: **온보딩(식비 진단·목표 설정·약한 카테고리) → 본 챌린지 진행 → 성공/실패 결과**
> 스택: Spring Boot 3.5 / Java 21 / JPA(Hibernate 6.6) / MySQL 8.4
> 상태: 설계 초안 · ERD 다이어그램은 `ERD.mermaid`(이 문서와 동기화) · 팀 합의 전 `열려있는 결정` 먼저 볼 것

---

## 1. 화면에서 읽어낸 규칙 (성공/실패 판정 모델)

Figma 7개 화면(식비 진단 / 목표 설정 / 약한 카테고리 / 성공·실패 각 2장)에서 확정된 동작:

**온보딩 STEP 1 — 식비 현실 진단**
- "지난달 식비가 얼마였나요?" 입력.
- 화면에 명시: **"입력값은 분석에만 쓰이고 저장되지 않아요."**
- → 이 값은 **DB에 저장하지 않음** (서버 API 불필요, 클라에서 추천 한도 계산용).

**온보딩 STEP 2 — 챌린지 목표 설정** (← 챌린지의 핵심 입력)
- 기간 선택: 7일 / 14일 / 30일 / 직접 입력(N일)
- 기간 내 식비 목표(예산): 예) 100,000원
- **하루 한도 = 목표 ÷ 기간** (예: 100,000 ÷ 30 = 3,333원) — 화면에서 자동 계산해 보여줌
- (30일 옵션) "월급날 기준으로 리셋" 토글 + 월급날(예: 25일)

**온보딩 STEP 3 — 나의 약한 카테고리**
- 카페/음료·디저트·배달·술자리·편의점 간식 + 직접 추가 중 **다중 선택**(수정 가능).
- "선택한 카테고리에 개입 강화" → **저장 필요**(사용처=지출 개입은 범위 밖, 저장만 일혁).

**성공 화면 (CHALLENGE COMPLETE) — 2장**
- 1장: "14일 챌린지 완주!" / 14·14 성공한 날 / **+68,200원 총 절약** / 14일 연속 달성 / 월 캘린더(성공·실패)
- 2장: 목표 대비 실제 사용(280,000 → 211,800) / **감정별 소비 패턴**(먹고싶어서 42%·스트레스 31%…)

**실패 화면 — 2장**
- 1장: "그래도 9일은 해냈어요" / 9 성공한 날 / 5 초과한 날 / **+24,100원 초과 금액** / 캘린더(성공·초과)
- 2장: **카테고리별 지출**(배달 38,400·카페 23,500·편의점 12,800) / **감정 인사이트** / 다음 목표 조정 제안

### 판정 로직 (정리)
- **하루 단위 판정**: `그날 식비 지출 합계 ≤ 하루 한도` → `성공`, 아니면 → `초과`
- **미입력일 = 0원 가정** (0630 회의 확정): 기록 없는 날은 0원 지출 → `성공` 취급 (매일 저녁 리마인더로 입력 유도)
- **챌린지 결과** (종료일에 확정): 모든 날 성공 → `SUCCESS`, 초과한 날 1일 이상 → `FAIL`
- 집계 값(저장 안 하고 조회 시 계산):
  - 성공한 날 = `count(성공)`, 초과한 날 = `count(초과)`
  - **총 절약 = Σ max(0, 하루한도 − 그날지출)**
  - **초과 금액 = Σ max(0, 그날지출 − 하루한도)**
  - 연속 달성 = 최장 연속 성공일 수

## 2. 의존성 (확정 범위 반영)

확정 범위(초기): 일혁=온보딩·본 챌린지·성공/실패 / 나연=미니챌린지·로그인 / 령준=햄배틀.
> ⚠️ **2026-07-05 분담표 확정** — 일혁 범위가 홈(소비 상태 알림)·위젯·미니 챌린지(완수 체크)·결과 AI 진단(?)까지 확장.
> **지출 입력·상세·분석 = 령준 확정** (초안 작성 시점의 "지출 담당 없음"은 해소됨).
> 이 문서는 계속 **본 챌린지** 범위만 다룸. 전체 분담표·신규 항목 매핑은 `역할변경_영향분석.md` 참고.

1. **회원(User)** — 로그인(나연)에서 오는 user 식별만 맞추면 됨(예: JWT subject).
   당장은 임시 userId로 시작하고 나중에 연동. (확정 기능이라 막힘 아님)

2. **지출 데이터 (`EXPENSE`, 외부)** — 성공/실패의 입력값. "일별 총액"만이 아니라 **`{날짜·금액·카테고리·감정}` 단위**가 필요:
   - 일별 판정 → 그날 지출 **합계**
   - 결과 화면 → **카테고리별 지출** + **감정별 비율** (`EXPENSE`를 group by)
   - **출처 = 령준 확정**(2026-07-05 분담표: 일일 지출 입력에 금액·감정 태그, 분석에 종류별 식비 — 필요한 필드 전부 존재).
     연동 방식은 **령준이 지출 합계 조회 메서드 제공, 일혁이 호출**로 결정(Claude, 단일 앱 전제) → `결정기록.md`.
   - 서버는 `EXPENSE` 입구(또는 조회)를 정의해 두고, 개발·테스트는 **시드 데이터**로 진행 → 답 기다리는 동안 안 막힘.

## 3. 엔티티 초안

### Challenge (챌린지 1건)

| 필드 | 타입 | 설명 |
|---|---|---|
| id | Long (PK) | |
| userId | Long (FK→User) | **의존: 나연** |
| durationDays | int | 3/7/14/31/N (프리셋은 스크린디자인 최신 기준, 2026-07-07) |
| startDate / endDate | LocalDate | endDate = startDate + durationDays − 1 |
| budgetTotal | int (원) | 기간 내 식비 목표 |
| dailyLimit | int (원) | **스냅샷** = budgetTotal / durationDays (버림) |
| resetByPayday | boolean | 월급날 리셋 옵션 (v2) |
| paydayDay | Integer (1~31, null 허용) | 월급날 |
| status | enum {IN_PROGRESS, SUCCESS, FAIL} | `@Enumerated(STRING)` |
| createdAt | LocalDateTime | |

> 💡 `dailyLimit`을 계산만 하지 않고 **스냅샷으로 저장**하는 이유: 나중에 목표·기간이 바뀌어도 과거 판정 기준이 흔들리지 않게 하기 위함 (정석).

### ChallengeDay (일별 판정 1행 — 캘린더·결과 집계용)

| 필드 | 타입 | 설명 |
|---|---|---|
| id | Long (PK) | |
| challengeId | Long (FK→Challenge) | |
| dayDate | LocalDate | 컬럼 `day_date` (date는 예약어라 회피) |
| spentAmount | int (원) | 그날 `EXPENSE` 합계 — **외부 의존** |
| status | enum {SUCCESS, OVER} | spentAmount ≤ dailyLimit ? SUCCESS : OVER |

제약: `unique(challengeId, dayDate)` — 하루 1행.

> 식비 진단(step1, 지난달 식비)은 저장 안 함 → 엔티티 없음. (약한 카테고리는 아래 엔티티로 **저장함**)

### ChallengeWeakCategory (약한 카테고리 선택 — 온보딩 STEP 3)

| 필드 | 타입 | 설명 |
|---|---|---|
| id | Long (PK) | |
| challengeId | Long (FK→Challenge) | |
| category | String | 카페음료/디저트/배달/술자리/편의점간식/직접추가 |

> 저장 단위는 **챌린지별로 확정** (`결정기록.md` — 서버는 선택값 저장만이라 단위 무관).

### Expense (외부 — 령준 소유, 범위 밖)

| 필드 | 타입 | 설명 |
|---|---|---|
| id | Long (PK) | |
| userId | Long (FK→User) | |
| spentDate | LocalDate | |
| amount | int (원) | 일별 합계·카테고리 집계 원천 |
| category | String | 카테고리별 지출용 |
| emotion | String | 감정 태깅(스트레스/보상/귀찮아서/그냥먹고싶어서/직접입력) · **null 허용**(건너뛰기, 와이어프레임 v2) |

> ⚠️ **일혁 소유 아님(령준 소유).** `ChallengeDay.spentAmount`와 결과 화면의 카테고리·감정 분석이 전부 여기서 파생. 연동 방식은 령준과 계약.

### 샘플 (Challenge 엔티티, 정석 형태)
```java
@Entity
@Table(name = "challenge")
public class Challenge {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private Long userId;            // 추후 @ManyToOne User 로 교체

    @Column(nullable = false)
    private int durationDays;

    @Column(nullable = false)
    private LocalDate startDate;
    @Column(nullable = false)
    private LocalDate endDate;

    @Column(nullable = false)
    private int budgetTotal;        // 기간 목표(원)
    @Column(nullable = false)
    private int dailyLimit;         // 스냅샷(원)

    private boolean resetByPayday;
    private Integer paydayDay;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false)
    private ChallengeStatus status; // IN_PROGRESS / SUCCESS / FAIL

    @Column(nullable = false)
    private LocalDateTime createdAt;
    // 생성자/정적 팩토리/연관관계 메서드는 구현 시
}
```

## 4. REST API 초안

| 메서드 | 경로 | 설명 | 대응 화면 |
|---|---|---|---|
| POST | `/challenges` | 챌린지 생성 (온보딩 step2 완료) | 목표 설정 |
| GET | `/challenges/current` | 진행 중 챌린지 + 현황(성공/초과 일수, 연속, 남은 일수) | 홈/진행 |
| GET | `/challenges/{id}/calendar?year=&month=` | 일별 성공/초과 기록 | 하루하루 기록 |
| GET | `/challenges/{id}/result` | 종료 결과(성공/실패, 절약·초과 금액, 연속, **카테고리·감정 분석**) | 성공/실패(2장) |
| POST | `/challenges/{id}/days` | 일별 지출액 수신(외부 입력) → 일별 판정(성공/초과) upsert | 일별 기록 |

- `POST /challenges` 요청 예: `{ durationDays, budgetTotal, startDate, resetByPayday?, paydayDay?, weakCategories[] }`
  → 응답: `{ challengeId, dailyLimit, endDate }`
- `POST /challenges/{id}/days` 요청 예: `{ date, spentAmount }`
  → 그날 지출을 받아 성공/초과 판정. **테스트/시드 전용 입구**(운영에선 서버가 령준 조회 메서드로 그날 합계를 스스로 가져옴 — `결정기록.md`).
- 식비 진단(step1): 저장 안 하므로 서버 API 없음.

## 5. 열려있는 결정 (팀과 먼저 합의)

1. **지출 데이터(EXPENSE) 연동 방식** — 출처=령준 확정, 방식=**령준 조회 메서드 호출**로 결정(Claude, 단일 앱 전제). 그동안 스텁+시드로 진행.
2. **약한 카테고리 저장 단위 (결정됨)** — **챌린지별 확정** (`결정기록.md`).
3. **User 연동 규약**: 로그인(나연)과 user_id 식별 방법(예: JWT subject)만 맞추면 됨. 당장은 임시 userId로 진행.
4. **`status` 확정 시점 (결정됨)**: `Challenge.status`는 생성 시 `IN_PROGRESS`. 종료 판정은 **배치 없이 `GET /result` 호출 시** 계산 — `end_date` 경과 후 ChallengeDay 전부 SUCCESS면 `SUCCESS`, OVER 1일+이면 `FAIL`. 최초 계산 시 컬럼에 저장(이후 재계산 생략).
5. **월급날 리셋**: 목표 설정 화면에 있는 기능이라 포함. 구현은 핵심 판정 API 다음 단계로(순서 문제).
6. **휴식 기능 (2026-07-06 재해석 확정)** — 휴식은 챌린지 일시정지가 아니라 **챌린지 사이의 공백(유저 단위 `user_rest`)**.
   `ChallengeStatus`는 IN_PROGRESS/SUCCESS/FAIL **그대로**(PAUSED·종료일 연장 안 함 — 초기 검토안 철회).
   상세: `와이어프레임v2_서버영향.md` §2 · `API명세_역할확장.md` §1~§3 · (구 미정이던 진입 규칙은 해소 — 휴식 진입점 = 결과 화면뿐, 역할확장 §1). Phase 1에는 영향 없음.

## 6. 추천 구현 순서 (일혁)

1. `Challenge` 엔티티 + 생성 API (`POST /challenges`) — User는 임시 스텁(하드코딩 userId)으로 시작
2. `ChallengeDay` 일별 반영 + 판정 로직 — 지출 연동은 임시 수동 입력 API로
3. 결과/캘린더 조회 API (`/result`, `/calendar`)
4. (팀 합의 후) 로그인 연동 + 지출 기능 연동으로 교체
5. (선택) 월급날 리셋

> 핵심: **혼자 끝까지 돌려보려면** 1~3을 임시 스텁으로 먼저 완성하고, 4에서 팀 것과 합치는 게 안전.
